# VQ2A8 routed experts

VQ2A8 is a DeepSeek V4 routed-expert format with 4-bit vector-quantization
codes, two weights per code, and FP8 codebooks. Its effective expert-weight
index storage is two bits per weight. Activations are dynamically quantized to
FP8 per token-expert assignment.

This backend currently targets NVIDIA Hopper (SM90+) with tensor parallelism.
Dense model weights continue to use vLLM's online FP8 methods; only routed
experts use the packed VQ2 path.

## Model configuration

Add the following entry to `config.json`:

```json
"quantization_config": {
  "quant_method": "vq2a8",
  "experts_path": "experts_vq",
  "kernel_path": "experts_vq_kernel"
}
```

`experts_path` is the producer artifact containing one JSON and safetensors
file per decoder layer. `kernel_path` is generated by the TP repacker.

## Repack for tensor parallelism

Run the repacker once, outside model startup:

```bash
python tools/repack_vq2_tp.py \
  --input /path/to/model/experts_vq \
  --output /path/to/model/experts_vq_kernel \
  --tp-size 4 \
  --num-experts 256 \
  --verify
```

The repacker resolves the producer permutation offline, shards gate/up output
rows and down input columns using vLLM's TP layout, and retains packed 4-bit
codes. `--verify` checks every repacked code and codebook selection before the
output is atomically installed. The source artifact is never modified.
Repeat the command with `--tp-size 1` or `--tp-size 2` when those serving
topologies are needed; each topology is stored in its own `tp1`, `tp2`, or
`tp4` directory.

## Backends

`VLLM_VQ2_BACKEND` selects the runtime:

- `decode_fp8` is the default compatibility path. It reconstructs BF16 expert
  matrices during loading and then uses the native online W8A8 MoE backend.
- `direct` loads TP-local packed VQ2 codes and performs VQ lookup with dynamic
  A8 execution. Layers whose artifact does not contain every routed expert
  automatically fall back to `decode_fp8`.

Example:

```bash
VLLM_VQ2_BACKEND=direct \
CUDA_VISIBLE_DEVICES=0,1,2,3 \
vllm serve /path/to/model \
  --tensor-parallel-size 4 \
  --compilation-config \
  '{"mode": 0, "cudagraph_mode": "FULL_DECODE_ONLY", \
    "cudagraph_capture_sizes": [1]}'
```

The direct backend currently supports TP with EP=1, eager execution or full
decode CUDA Graph capture, packed gate/up layout, SiLU/SwiGLU clamp, and no
routed-expert LoRA. Keep
`decode_fp8` available while bringing up a new model artifact or topology.

### CUDA Graph decode

For latency-sensitive decode, use `FULL_DECODE_ONLY` CUDA Graph capture and
leave torch compilation disabled. The current DeepSeek V4 model class does not
advertise Dynamo/Inductor compatibility, but this does not prevent full decode
graph capture. The direct VQ2 CUDA and Triton operators are graph safe.

Run the reproducible steady-state benchmark with an activated environment:

```bash
export CUDA_HOME="${CUDA_HOME:-/usr/local/cuda}"
export PATH="$CUDA_HOME/bin:$PATH"
export LD_LIBRARY_PATH="$CUDA_HOME/lib64:${LD_LIBRARY_PATH:-}"
CUDA_VISIBLE_DEVICES=0,1,2,3 \
python tools/benchmark_vq2a8_graph.py \
  --model /path/to/model \
  --tensor-parallel-size 4
```

The benchmark captures batch size one, warms up generation, and then reports
five 16-token measurements. On the initial TP4 H200 test, the mean increased
from 8.86 tokens/s in eager CUDA-auto mode to 55.75 tokens/s with CUDA Graphs.
Enabling vLLM custom all-reduce on the NVSwitch-connected TP4 group increased
the mean again to 58.45 tokens/s. The benchmark enables custom all-reduce by
default; pass `--disable-custom-all-reduce` to reproduce the NCCL-only result.
Treat these values as checkpoint- and hardware-specific rather than universal
thresholds.

For service throughput, capture the intended concurrency sizes and measure
them in one model load:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
python tools/benchmark_vq2a8_concurrency.py \
  --model /path/to/model \
  --tensor-parallel-size 4 \
  --concurrency 1,2,4,8,16,32
```

### TP and DP topology selection

On four NVSwitch-connected H200 GPUs, use one TP4 instance for general serving
and especially for 32 or more simultaneous decode sequences. Splitting the
GPUs into smaller TP groups is useful only at low total concurrency:

| Total concurrency | TP4 | TP2 x DP2 | TP1 x DP4 |
|---:|---:|---:|---:|
| 2 | 135.53 | 150.99 | - |
| 4 | 225.49 | 225.56 | 236.68 |
| 8 | 321.25 | 340.51 | 323.06 |
| 16 | 455.99 | 464.35 | 461.40 |
| 32 | 1698.54 | 564.45 | 569.03 |

Values are aggregate output tokens/s from three steady 64-token measurements.
The sharp TP4 increase at concurrency 32 occurs when 32 sequences times top-k
6 reaches the 192-assignment grouped VQ2 threshold. Avoid splitting those
requests across replicas if doing so leaves every replica below that threshold.

Observed weights plus non-Torch memory were 25.24 GiB/rank for TP4, 46.71
GiB/rank for TP2, and 88.76 GiB for TP1. TP1 required
`--gpu-memory-utilization 0.8` to reserve a useful KV cache on a 140 GiB H200.

### Adaptive direct execution

The direct backend combines optional CUDA C++ kernels with Triton kernels and
selects the fastest measured path using the number of token-expert assignments:

- CUDA C++ performs the expert-specific FWHT, scaling, bias reduction, and
  dynamic FP8 quantization whenever the extension is available.
- Up to 12 assignments, CUDA C++ also fuses the packed down GEMM, route
  weighting, FP32 token reduction, and BF16 output conversion.
- Below 192 assignments, gate/up uses the lower-register-pressure Triton
  batched GEMM plus a PyTorch SwiGLU epilogue. Down uses its fused Triton
  reduction above the 12-assignment CUDA crossover.
- At 192 or more assignments, `moe_align_block_size` groups tokens by expert.
  Each Triton program then computes a real `[16, 32]` output tile for one
  expert instead of broadcasting a single assignment to a Tensor Core tile.
  The same alignment is reused for gate/up and down.

The thresholds are based on the initial TP4 Hopper measurements. Re-profile
them when the expert count, topology, or production batch distribution changes.

### Build the CUDA C++ extension

The extension targets Hopper `sm_90a` and uses the CUTLASS headers already
vendored under `vllm/third_party/deep_gemm/include`. Build it inside the vLLM
checkout with a Python environment that provides a CUDA-enabled PyTorch build:

```bash
export CUDA_HOME="${CUDA_HOME:-/usr/local/cuda}"
export PATH="$CUDA_HOME/bin:$PATH"
export TORCH_CUDA_ARCH_LIST=9.0a
python tools/build_vq2a8_cuda.py \
  --source csrc/vq2a8/prepare_activation.cu \
  --build-dir .vq2a8_cuda_build \
  --output vllm/_vq2a8_cuda_ext.so
```

`VLLM_VQ2_PREP_BACKEND=auto|cuda|triton` controls activation preparation, and
`VLLM_VQ2_GEMM_BACKEND=auto|cuda|triton` controls the fused down-reduce path.
`auto` is recommended. `cuda` forces that implementation for debugging and
correctness tests; it deliberately bypasses the measured crossover threshold.
Set `VLLM_VQ2_CUDA_LIBRARY` only when the shared library is stored somewhere
other than `vllm/_vq2a8_cuda_ext.so`.

## Validation

The required acceptance checks are:

1. Producer decoder and vLLM compatibility decoder are BF16 bit-identical.
2. TP-local repacked gate/up and down matrices are BF16 bit-identical to the
   corresponding decoded TP shards.
3. Batched packed GEMM matches the single-expert VQ2A8 reference.
4. A real TP generation completes with the direct backend.

On the initial DeepSeek V4 Flash TP4 bring-up, direct VQ2 reduced model weight
memory from 68.28 GiB to 23.99 GiB per rank and model loading from about 537
seconds to 47 seconds. These numbers are hardware and checkpoint dependent.
